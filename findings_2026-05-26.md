## 1. Smoke v3 run status and why 33/36 finished while 3 are stuck

### Root cause of the split

All 36 smoke v3 runs launched on 2026-05-25 ~11:40–12:10 and simulated fresh traces into
`traces_smoke_v3_{mode}_sigma{X}/` (the original paperscale_v2 trace dirs are gone, so fresh
simulation was necessary for all 36). Simulation + R2 detection completes in ~2–3h at smoke
scale. Wall-clock time to COMPLETE was ~10–12h for the successful runs.

The 3 stuck runs (f9 σ=3.0, σ=3.5, σ=4.0) completed simulation and detection but **failed the
automatic ICS archive validation check** (`check_ics_archive.py`) that the pipeline runs before
training starts. The configured level (90, placeholder from the env files) produced empty ICS
arrays for these high-noise f9 runs → pipeline exited with:

```
ERROR: ICS archive validation failed.
Hint: lower SHA3_TRAINING_ICS_LEVEL (for example 10) or regenerate traces/detection with stronger signal.
```

The 33 completed runs all passed the check at level 90 (hd/hw/id all sigmas, f9 σ=0.1–2.5).

**Note on `sim_steps=0` confusion:** Grepping log files for "SIM:" lines (pipeline log-function
prefix) misidentified all runs as having skipped simulation. The KeccakSim output is raw stdout
without that prefix — first log lines like `bulk_samples=160` confirm simulation did run for all
36. The correct check is `grep "^\[" | head -1` to find the first timestamped pipeline action
(which follows simulator output).

## 2. Smoke-scale ICS boundaries for f9 (10 detection sets)

Found by scanning all 9 archive levels (090→010) after detection completed:

| Sigma | Smoke v3 (10 det) max valid | Midscale v1 (30 det) max valid | Direction |
|-------|----------------------------|-------------------------------|-----------|
| 3.0   | **70**                     | 70                            | same      |
| 3.5   | **60**                     | 50                            | smoke HIGHER |
| 4.0   | **50**                     | 40                            | smoke HIGHER |

### Interpretation

Counterintuitive: fewer detection sets (10 vs 30) allows a *higher* ICS threshold at σ=3.5/4.0.
Likely explanation: with only 10 detection sets, the R² correlation estimates have high variance.
Some sample positions get inflated R² values by chance, crossing the threshold even at stricter
levels. This means ICS samples identified at smoke scale may be partially driven by noise rather
than true signal — they exist and cover all words, but are less reliable than ICS selected with
30+ detection sets.

**Implication for paperscale (100 det sets):** Expect the R² signal to be stronger than
midscale. The per-sigma f9 boundaries at paperscale may be AT OR ABOVE the midscale values
(70/50/40). The env file placeholders (70/50/40) are conservative baselines — verify after
detection with `launch_paperscale_v3.sh --ics-scan`.

**Implication for smoke v3 comparison:** The smoke v3 f9 σ=3.5/4.0 runs will train at levels
60/50, while midscale used 50/40. These are not the same "per-sigma standard". The smoke v3
ICS boundary scan thus does NOT directly confirm that level 50/40 is appropriate for paperscale
at these sigmas. The midscale boundary (30 det sets) is the more reliable reference because its
R² estimates are less noisy.

### Action: fix f9 σ=3.0/3.5/4.0 smoke v3

ICS levels to apply: σ=3.0→70, σ=3.5→60, σ=4.0→50 (highest passing at smoke scale).
Re-run training+val+SASCA with `run_overnight_chain.sh --with-training`.

## 3. Midscale fix run timing — why so slow

The 11 midscale fix sessions (+ f9 σ=3.5 original) are running `--skip-detection` (training,
val, SASCA only) but midscale scale is much larger than smoke:

| Stage        | Smoke v3  | Midscale v1 | Ratio |
|--------------|-----------|-------------|-------|
| Training sets| 50        | 200         | 4×    |
| SASCA traces | 50        | 300         | 6×    |
| Rate points  | 21        | 101         | 5×    |
| Rate step (bits) | 64    | 16          | 4× more resolution |

Training (IoPs + template profiling) takes ~6–8h at midscale vs ~1h at smoke scale.
SASCA (300 traces × rate+iteration scans for 2R/3R/4R) takes ~8–12h vs ~2h at smoke.
Total midscale wall-clock: ~16–20h per fix run.

Fix runs launched ~11:30 on 2026-05-25. Expected COMPLETE ~06:00–08:00 on 2026-05-27.

### Also discovered during status check: pack.sh octal bug

When ICS fix was applied via `sed -i 's/SHA3_VALIDATION_TEMPLATE_TAG=.*/...=070/'`, the
3-digit value `070` in the shell env file was interpreted as **octal 56** by
`printf '%03d' "${SHA3_VALIDATION_TEMPLATE_TAG}"` in `pack.sh`, producing
`templateLDA_O056.zip` instead of `templateLDA_O070.zip`. Level 90 escaped this because
`090` contains `9` (invalid octal digit) and bash fell back to decimal.

**Affected runs:** f9 σ=3.0 (created O056.zip), f9 σ=4.0 (created O032.zip). Both failed at
the validation `unzip` step. Recovery: re-ran `pack.sh` after fixing `.env` tags to plain
integers (`70`, `40`), then restarted `run_overnight_chain.sh`. Both are now in SASCA.

**Fix applied:** `pack.sh` now uses `$((10#${SHA3_VALIDATION_TEMPLATE_TAG:-10}))` to force
decimal. `fix_ics()` in `launch_paperscale_v3.sh` updated to write plain integers. Committed
as `e7b1e67`.
